# Security

This repository is the Hackney Hackers studio site — static HTML served by
GitHub Pages at [hackneyhackers.com](https://hackneyhackers.com). Nothing here
runs on a server, and the site holds no accounts, sessions or personal data of
its own.

## Reporting something

Email **support@hackneyhackers.com**. Plain email is fine — no special format,
no bounty programme. Tell us what you found and how you found it, and we will
read it and reply.

If you are reporting something that affects people using one of our apps
rather than this site, say so; those live in other repositories and we will
route it.

## The Google API key in `index.html`

Automated scanners flag this, so it is worth writing down once.

The World of Pomos waitlist form posts to Cloud Firestore, and the key in the
page identifies the Firebase project it posts to. **It is a public client
identifier, not a credential.** Firebase web keys are designed to ship in
client code; the same key is served in the World of Pomos web app bundle. It
grants nothing on its own.

Access is controlled by Firestore security rules, not by possession of the
key. For the `waitlist` collection those rules allow an unauthenticated
*create* only when:

- the document has exactly the fields `email`, `createdAt`, `source`, `status`
- `email` is a string of 4–254 characters, shaped like an address
- `status` is `pending`
- `createdAt` equals the server's own clock, so entries cannot be backdated

Reads, listing and deletes are all denied. The collection cannot be
enumerated, so signups cannot be harvested from the page.

The key additionally carries an allowlist of the Google APIs it may be used
against, and an HTTP referrer allowlist. One caveat worth knowing if you are
testing: **Cloud Firestore does not enforce API-key referrer restrictions** —
requests from any origin reach it and are then judged by the rules above.
Identity Toolkit does enforce them, so the key cannot be lifted from this page
and used to drive Firebase Auth from elsewhere.

### What would be a real finding

- Reading, listing or exporting the `waitlist` collection
- Writing a document that escapes the schema above
- Using the key against a Google API outside its allowlist
- Anything that reaches data belonging to a person using our apps

### What is not

- The presence of the key in this repository or in the page source
- A scanner reporting `google_api_key` against `index.html`

Both are expected. If you have found a way to make the key do something the
rules do not permit, though, that is very much worth an email.

## Scope

In scope: this repository and the site it publishes.

Out of scope: findings that require a compromised device or browser
extension, denial of service, missing hardening headers with no demonstrated
impact, and reports generated by a scanner with no accompanying explanation of
the actual risk.
